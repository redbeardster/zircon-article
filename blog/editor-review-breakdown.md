## A. Расхождения с настоящим Zircon

### A1. Кому принадлежат права — **верно**
- **Проблема.** Текст утверждал, что в Fuchsia права принадлежат записи объекта; документация: *«Rights are associated with handles»*.
- **Почему важно.** Оговорка переворачивала отношение модели к реальности.
- **Исправление.** §3.1: права ассоциированы с handle; склейка `capability = handle` — учебное упрощение представления слота.

### A2. У `zx_channel_write` нет аргумента прав — **верно**
- **Проблема.** Фраза «в духе документации Zircon» скрывала, что обычный write не принимает маску; урезание — через `_etc` / duplicate/replace; сверх исходных → `ZX_ERR_INVALID_ARGS`, не ∩.
- **Исправление.** Явная оговорка после обсуждения move; модель использует `reduce_rights_wf` как учебный оператор ослабления.

### A3. Атомарность при ошибке — **верно (критично)**
- **Проблема.** В Zircon handles сбрасываются *on success or failure*; в модели `None` = состояние не меняется. Текст подавал второе как ключевое свойство без контраста.
- **Исправление.** §4, п.1 списка: учебный выбор vs реальное поведение; указан `zx_channel_write_etc` для сохранения handles при отказе.

### A4. Duplicate без `DUPLICATE` — **верно**
- **Проблема.** В модели не было проверки `ZX_RIGHT_DUPLICATE`.
- **Исправление (теория + текст).** В `zx_handle_duplicate` обязателен `ZX_RIGHT_DUPLICATE`; лемма `zx_handle_duplicate_requires_duplicate_right`; §5.3 и граница модели отражают это.

### A5. Канал: два конца vs одна очередь — **верно**
- **Проблема.** Оба endpoint смотрели на один `obj_id` / одну очередь → возможен self-read.
- **Исправление (теория + текст).** `channel_peer`: write → очередь пира, read → своя; §3.1 и §11.5 синхронизированы с экстрактом.

### A6. MMIO «запрещён архитектурно» — **верно**
- **Проблема.** В Fuchsia MMIO идёт через `ZX_RSRC_KIND_MMIO` + physical VMO, а не «запрет».
- **Исправление.** §2.2 переписан; §9 явно: гипотетический немедиируемый poke, не модель реального пути.

### A7. Wi-Fi vs модем через MMIO — **верно как «сомнительно»**
- **Проблема.** Тезис «в отличие от Wi-Fi модемы через MMIO» не проверен; оба класса драйверов часто используют MMIO.
- **Исправление.** §2.2: оба через MMIO; модем — как точка совместимости из обзора, без ложного контраста.

## B. Несовпадения с теориями

### B1. Трассовая теорема «сильнее» пошаговой — **верно; закрыто структурно**
- **Факт (старый).** В `reachable_transfer_no_escalation` из `reachable` выводился `state_wf s`, но для no-escalation он **не использовался**.
- **Исправление.** Syscall'ы больше не проверяют `rights_wf` источника (как Zircon). Пошаговая лемма принимает предпосылку явно; трассовая извлекает её из `handles_wf ⊆ state_wf` достижимого состояния (`handles_wf_lookup`). Без трасс предпосылка висела бы. Текст §5.2 и §14.4 переписан.

### B2. Таблица условий-стражей про `rights_wf` — **верно (ошибка содержания)**
- **Факт.** `reduce_rights_wf` всегда даёт wf-маску (`close_rights_wf`). Без проверки `rights_wf` у источника ломается **no-escalation** (пример: src `{WRITE,TRANSFER}`, req `{WRITE}` → `{READ,WRITE}`).
- **Исправление.** Шаг 2 §4.1 и строка таблицы `tab:write-guards` переписаны под эскалацию через замыкание.

### B3. Как доказана главная теорема — **верно**
- **Факт.**
  - `channel_transfer_no_escalation` = `transfer_via_channel_no_escalation` + `by blast` (⊆ → ¬∃).
  - Содержание: `transfer_via_channel_cap` + `reduce_rights_wf_le_old` (+ `rights_wf` из `zx_channel_write_success`).
  - `transfer_rights_eq_meet` в Lattice **не** участвует в доказательстве ядра.
  - Аннотация «ключевые леммы = следствия решётки» — преувеличение.
- **Исправление.** §5.2 переписан по фактическому пути; аннотация смягчена; meet оставлен как параллельная иллюстрация.

### B4. Листинг `ht(pay ↦ None)` — **верно**
- **Факт.** В теории удаление слота: `ht(pay_hid := None)`; `↦` для option-map означает `Some _`.
- **Исправление.** Листинг §4 и шаг 4: `:= None`.

### B5. Замыкание / направления iff — **верно**
- **Проблема.** Смысл «не изобретает прав» относится к `wf ⇒ close = id`, а был приписан обратной стороне.
- **Исправление.** §13.3 п.4: первая импликация = «не изобретает»; обратная = полнота характеризации.

### B6. Мелкие несовпадения — **в основном верно**

| Пункт | Вердикт | Что сделано |
|--------|---------|-------------|
| Типы `Hardware`, `Other_Obj` | верно | Добавлены в онтологию §3.1 |
| id 7/3 vs сценарий 0/1 | верно | §4.1: «иллюстративный микропример», не «совпадает со §6» |
| OCaml `system_state` vs `unit system_state_ext` | верно | Оговорка в §11 |
| `assert Zircon…` vs `Zircon.Zircon` + PASS/FAIL | верно | Листинг приведён к `generated/test_example.ml` |
| duplicate в «ядре», но не в трассах | закрыто | Метки `Duplicate`/`Close` в `step`; `reachable_duplicate_no_escalation` |
| `reduce_rights_idempotent` = ассоциативность | верно в теории | Переименовано в `reduce_rights_compose` |
| Подпись рис. 2 без замыкания | верно | «замкнутое пересечение (`reduce_rights_wf`)» |
| «не покрывает MMIO» vs §9 | верно | §2.3: MMIO только как контрпример обхода |

### B7. Трудозатраты 500–1000 + 300–600 vs 1881 — **верно**
- **Исправление.** Убраны заниженные диапазоны; в статье — порядка 2500 строк (факт: 2522 по шести теориям, 2026-10-15).

## D. Что внесено в теории (2026-10-15)

В `Zircon.thy` (сборка `isabelle build -d . Zircon` — OK):

| Было (упрощение) | Стало в теории |
|------------------|----------------|
| Одна очередь на общий `obj_id` | Два endpoint + `channel_peer`; write → очередь пира, read → своя |
| Нет проверки `DUPLICATE` | `ZX_RIGHT_DUPLICATE` обязателен в `zx_handle_duplicate` |
| Тихое ∩ при любом `req` | `req ⊆ h_rights`, иначе `None` (аналог `INVALID_ARGS`); затем `reduce_rights_wf` |
| — | Леммы: `channel_write_fails_unless_subset`, `zx_handle_duplicate_requires_duplicate_right`; обновлены success/cap |
| `rights_wf` как страж syscall | Снято; инвариант `handles_wf`; трассы дают посылку no-escalation |
| Нет топологии пиров | `peers_wf` (симметрия, очереди, id < `next_obj_id`) |
| Нет меток Duplicate/Close | Обе в `step`; `exec_step_preserves_wf` покрывает |

**Сознательно оставлено учебным** (только в тексте теории/статьи):
- `None` при ошибке write = состояние не тронуто (не «discard on failure» Zircon);
- MMIO-poke остаётся гипотетическим обходом, не `ZX_RSRC_KIND_MMIO`;
- нет refcount на объект: close = удаление слота, не `zx_handle_replace` целиком.

## H. Структурный раунд (2026-10-15, вечер)

После ревью «ещё раз с учётом замечаний и реального Zircon»:

**Модель.**
- Syscall'ы (`zx_channel_write`, `zx_handle_duplicate`) больше не проверяют `rights_wf` источника. Реальный Zircon тоже: `zx_channel_write_etc` проверяет subset (`ZX_ERR_INVALID_ARGS`), не «корректность маски».
- `state_wf = handles_wf ∧ channels_caps_wf ∧ peers_wf`. `peers_wf`: симметрия `channel_peer`, обе очереди существуют, id < `next_obj_id`.
- Пошаговые no-escalation требуют `rights_wf` явно; контрпример `transfer_without_wf_source_may_escalate`.
- Трассовые теоремы извлекают посылку из `handles_wf` достижимого состояния. `state_wf` на трассах — не упаковка, а источник предпосылки.
- Метки `Duplicate`/`Close`; `reachable_duplicate_no_escalation`; учебный сценарий как трасса (`example_trace_reachable_wf`).
- `alloc_hid` с 1 (0 = `ZX_HANDLE_INVALID`).

**Доказательства (зацикливание simp).**
- Раскрытое `peers_wf` даёт симметричное условное правило; `simp`/`auto` с посылкой `peers_wf s` зацикливаются.
- Фикс: `peers_wfD` (blast), `peers_wfI`, `peers_wf_cong` (связь не менялась / очереди не исчезали / счётчик не убывал). `peers_wf_def` не в simp-set вместе с посылкой.
- Ранее: `reachable_trans` с `auto intro: reachable.step` тоже зацикливался (схематичное промежуточное состояние) — явная Isar-индукция.
- Сборка: `isabelle build -d . Zircon` — 16 с elapsed; `make test` — PASS.

**Текст.** §3.1 `state_wf`/`peers_wf`; §5.2 посылка из трасс; §5.3 duplicate без стража + `zx_handle_replace`; §8.5.1; §9 MMIO/BTI; §11.5; §13 ядро/границы; §14.4 трассы реально работают.
